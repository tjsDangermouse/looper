# Phase 4a — findings and the proposed 4b list

Data: [`parity-4a.md`](./parity-4a.md) (regenerated by `bench/parity.ts` +
`bench/parity-legs.ts`). Raw remote responses in `parity-4a-remote.json`,
raw leg data in `parity-4a-legs.json`. On-device side captured with
`LOOPER_LIVE_OVERPASS=1 LOOPER_PARITY_OUT=… swift test --filter Phase4ParityTests`
against `overpass.osm.ch`; remote side is the live `/v1/loops`; the leg ceiling
is a local GraphHopper (`docker start looper-graphhopper-iom-1`).

This run is **after** the snapping / tie-break / hysteresis commit (`796d342`).

---

## Headline

**The engines agree on leg length; they disagree on how much of the walk is
pavement, and the leg-routing ceiling says that gap is graph *content* (C2),
not the cost function (C1).**

The clearest evidence is the leg ceiling:

| leg | metres Δ | pave % (gh / device) | corridor overlap |
|---|---|---|---|
| onchan | **0%** | **70.3 / 70.3** | **100%** |
| douglas-seafront | +0.1% | 96.7 / 56.7 | 69.7% |
| douglas-inland | −3.1% | 87.5 / 50.4 | 72.2% |
| peel-control | — | 98.8 / _(endpoint unsnappable on-device)_ | — |

Where the Overpass graph and GraphHopper's import describe the same ground
(`onchan`), `LocalLegRouter` is **byte-identical** to GraphHopper — same
distance, same pavement share, same hops. The C1 port (weighting shape,
snapping, tie-break, hysteresis) is sound.

Where they differ (`seafront`, `inland`), the on-device walk follows almost the
same corridor but is scored 30–40 percentage points less "on pavement", and on
`peel-control` GraphHopper routes from an endpoint the Overpass graph cannot
snap to at all. That is the separately-mapped-pavement problem: the promenade
and inland pavements GraphHopper walks are either missing from the Overpass
fetch, severed by the chunk halo, or pruned by `minNetworkSize: 200`.

The ring fixtures echo it — on-device pave% is lower on every Douglas fixture
(57.7 vs 72.2, 59.8 vs 76.1, 50.3 vs 84.2, 76.1 vs 86.6, 65.9 vs 88.4).

## Secondary observations

- **On-device rejects far more candidates as `shapeless` / `out-and-back-spur`.**
  `onchan-5km`: remote rejects nothing (`{}`), on-device rejects 32.
  `peel-5km`: 71 `shapeless` vs 8; only 2 routes offered vs 3.
  `douglas-5km`: 22 vs 5. Either candidate generation is producing worse
  shapes, the sparser graph forces uglier legs, or both. Needs a look.
- **`sameWalk%` is low on mid-size Douglas loops** (32–38% for 4/5 km, onchan,
  prom) but high on `douglas-8km` (85%) and `peel-5km` (96%). The two engines
  frequently offer *different* loops. Some of that is legitimate (a heuristic
  sweep fans out small per-edge cost differences over a whole loop); some may
  be a candidate-generation or diversity-selection divergence. Not attributable
  from aggregate numbers alone — needs per-pair inspection.
- **U-turns**: on-device reports 1–2 where remote reports 0 on
  `douglas-4/5/8 km`. Expected — C3 (no turn signs; geometry-only detection is
  more trigger-happy). Already documented.
- **Distance error is *better* on-device** on most fixtures (3.8 vs 6.0,
  0.8 vs 6.0, 3.1 vs 4.6). Not a concern.
- **Waypoint fixtures** miss the target badly on *both* engines (13–18%),
  matching the known waypoint-mode distance problem. On-device `wp2` is rougher
  (2 offered, 20 u-turn rejections, 43% worst-overlap).
- **`peel-5km` on-device is unrepresentative** — 71 `shapeless` rejections, 2
  routes offered; its 82.5% pave (higher than remote's 59.6%) is a thin,
  self-selected slice, not a real inversion.

## Proposed 4b changes, ranked by evidence

1. **Close the C2 pavement-content gap (biggest lever).** The leg ceiling
   isolates it: identical where graphs agree, 30–40 pts apart where they don't,
   plus an unsnappable endpoint. Investigate, in order:
   a. `minNetworkSize: 200` subnetwork pruning — is it dropping sidewalk
      sub-networks that only connect through unmapped crossings?
   b. crossing modelling (C2, already flagged open in the audit) — without
      `highway=crossing` connectivity the sidewalk graph only touches the road
      graph at corners.
   c. chunk halo / seam truncation near `peel-control`.
   d. OSM currency (Overpass live vs the GraphHopper import date).
   Measure each against this same harness.

2. **Investigate the `shapeless` / spur rejection excess** (`onchan-5km`,
   `peel-5km`). Compare on-device candidate geometry to remote's for one
   fixture; decide whether it's candidate generation, the gate, or a
   consequence of (1).

3. **Attribute the low `sameWalk%` on mid-size Douglas loops.** Pick
   `douglas-5km`, lay the three remote offers beside the three on-device offers,
   and classify each mismatch: C2, C3, or a mismatched rule. This is the
   plan's actual parity gate and it needs eyeballing, not a metric.

4. **Calibrate the C1 constants — low priority.** `distance_influence` and
   per-way `foot_average_speed` are still unported, and the two new constants
   (`pedestrianSnapBiasMetres = 4`, `classSwitchPenaltyMetres = 15`) are
   defaults. The leg ceiling shows length parity is already there
   (onchan 0%, seafront +0.1%), so this is real correctness housekeeping but
   not what is costing pavement. Sweep with `bench/probe-pavement.mjs`'s method
   once (1) is done, so the graph isn't a confound.

## Re-running

```
docker start looper-graphhopper-iom-1
OUT=$(mktemp); : > "$OUT"
( cd ios/LooperKit && LOOPER_LIVE_OVERPASS=1 LOOPER_PARITY_OUT="$OUT" \
    swift test --filter Phase4ParityTests )
( cd route-service && npx tsx bench/parity.ts --ondevice "$OUT" \
    && npx tsx bench/parity-legs.ts --ondevice "$OUT" )
```
